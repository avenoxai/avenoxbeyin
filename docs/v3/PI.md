# Pi harness

Pi (`@earendil-works/pi-coding-agent`) is distinct from OMP (Oh My Pi). The installer
writes `.pi/extensions/beyin-v3.ts`, generated by
`template/.claude/scripts/beyin_v3_pi.py`. It uses the existing Python lifecycle,
retrieval and receipt engine; no npm dependency, model service or daemon is added.
The adapter targets the Pi 1.3 extension contract (`agent_before_settle` and
`before_agent_start.messageType`). Older Pi versions are not an established target.

## Product scope and equivalence acceptance

This is a distributable client adapter, not a configuration for one operator.
Installer-generated vault/interpreter paths belong to each installation; no personal
identity, machine path or separate memory engine is built into the source. The same
package must work in an unrelated user's independently installed vault.

Equivalence means the same shared Beyin capabilities under the **same scope and
preferences**, with delivery translated to Pi's API. The supported Claude/Codex
vault-local hooks and existing global bridge are the reference, not a reduced
Pi-only feature set. Global bridges for those clients also intentionally omit
per-turn retrieval, editor tracking and forced receipt reminders; keeping that
common boundary in Pi is not a Pi-specific capacity reduction.

| Capability | Pi contract / evidence |
|---|---|
| Companion opening and prompt retrieval | Same shared context; direct Claude/Codex/Pi output comparisons |
| Normal/economical/manual and context modes | Shared preferences; same-event comparisons across profiles/modes |
| Edits, receipts and knowledge distillation reminders | Shared edit windows, receipts and once-only reminder logic; Pi continuation/knowledge tests |
| Post-edit hygiene notices | Same opt-in warning; appended to Pi tool-result content without dropping original or structured output |
| Compaction/shutdown metadata | Same shared queue events, driven through generated Pi handlers |
| Privacy/no-memory/scope boundaries | Same private/untrusted gates and explicit no_memory behavior; Pi invocation opt-out and unrelated-vault checks |
| External project bridge | Same bootstrap and project/session namespace as Claude/Codex, not automatic personal-history injection |
| Distribution lifecycle | Independent second-user installation, managed exclusions, conflicts, upgrade/rollback and uninstall |
| Skills and agent-owned learning | Existing shared skill/protocol; no claim that a model always follows instructions correctly |

The table is an acceptance contract, not a blanket claim of verified live delivery.
Offline contract results, actual Pi loader/runner results, native-platform CI and
cold-client model tests must be reported separately. The generated-extension CI
job runs on Linux, macOS and Windows; defining that matrix is not evidence that
remote runs have passed. Do not call the integration fully verified or released
while the native/live gates remain open.

## Vault-local use

Install V3 normally, open Pi in the vault, review the generated extension and grant
project trust. Pi loads `.pi/extensions/` only after that trust decision. Choosing
"Trust" in the interactive prompt saves the decision in `~/.pi/agent/trust.json`;
print, JSON and RPC modes cannot ask and skip project resources without a saved
decision or `--approve`. A folder trusted before this update (the installed
`.agents/skills/` already asks for trust) loads the new extension without a new
prompt. Start a new session (or `/reload` after an update). The shared skills are
already installed in `.agents/skills/`, which Pi discovers; no duplicate
`.pi/skills/` tree is needed.
Pi reads the existing `AGENTS.md` companion instructions.

The installer owns the extension, including its original bytes and checksum in
`v3-install.json`. Reinstall/update refuses unreviewed custom edits. Rollback and
uninstall restore/remove it through the existing transaction system.
`--exclude-component adapters/pi` (or `preferences --exclude-component adapters/pi`,
followed by install/update) excludes this adapter; `adapters` excludes it with the
other optional adapters. User-owned `.pi/settings.json` is never rewritten.

Releases up to 3.11.0 do not know Pi. Before a rollback or uninstall to such a
release, remove the extension path from personal Pi settings and `pi -e` aliases
(a removed file makes Pi reject `--beyin-project-root` and exit) and re-include
`adapters/pi` if you excluded it (the older installer rejects the unknown name).
Receipts written with `--harness pi` stay on disk and in the receipt views, but the
older `sync` reports them as `invalid harness: pi` (`degraded`, doctor
`needs_attention`) until the next update.

The extension pins the vault and Python interpreter at install time. `BEYIN_PYTHON`
can override the interpreter. State is read from `.beyin-runtime.json` and must be
absolute. A missing/broken locator registers no lifecycle handlers. Subprocesses
have a 6 second POSIX / 20 second Windows bound; launch failure, timeout, non-zero
exit or malformed output gives no context and never fails a Pi turn.

## Lifecycle mapping

| Pi event | Shared event / delivery |
|---|---|
| `session_start` | `SessionStart`; context held until the first user run |
| `before_agent_start` with `messageType: "user"` | `UserPromptSubmit`; returned custom message carries context |
| successful `tool_result` for `edit` or `write` | `PostToolUse`, including the editor path; returned hygiene context is added to the tool result |
| `agent_before_settle` | `Stop`; a shared receipt/learning reminder becomes a custom-message entry with `continue: true` |
| `session_before_compact` | `PreCompact`; Pi still owns compaction |
| `session_shutdown` | `SessionEnd`; also emitted on reload/session replacement |

Custom-message-started runs are not user prompts and do not start retrieval. Failed
writes and read tools are not edits. Aborted/failed settlement still records Stop
but never spends a reminder or requests continuation. After a completed assistant
reply, `context.canContinue` is normally false until the reminder entry is added;
Pi validates continuation against that updated context. The shared
once-only reminder markers bound continuations; no unconditional model loop is added.
New/resumed/forked sessions get their own real `ctx.sessionManager.getSessionId()`;
an absent or `unknown` ID queues nothing. Pi supplies `PI_SESSION_ID` to its standard
shell tools, so successful `beyin.py note-create/task-create/task-update` shell
writes also open the matching receipt reminder window. Shell tools that do not
expose the session ID cannot provide this automatic association.

The agent submits `receipt --harness pi --session SESSION ...`, using the receipt
session from injected context (the shared runtime's hash, not a guessed ID).
Lifecycle queues retain metadata only, never prompt/transcript/tool-result text.
Retrieval is the same as for the other clients, including private/untrusted gates.
Delivered context becomes part of the normal Pi conversation; this does not redact
or control Pi's own session storage.

`--beyin-no-memory` disables all adapter injection and lifecycle bookkeeping for one
Pi invocation, including Stop and shutdown. Shared Beyin preferences and
`BEYIN_V3_SKIP` / `BEYIN_V3_INTERNAL` still apply. Natural-language privacy requests
remain agent instructions, not a natural-language classifier in the adapter.

## Explicit bridge from another project

By default the extension does **nothing outside the exact canonical vault cwd**.
Do not copy it to a global directory or install a second engine in each project.
For an authorized external project, load the vault-owned extension explicitly:

```sh
cd /path/to/project
pi -e /path/to/vault/.pi/extensions/beyin-v3.ts --beyin-project-root /path/to/projects
```

`--beyin-project-root` accepts one absolute directory. For several independent
roots use `--beyin-project-roots '["/path/to/work", "/path/to/other-projects"]'`;
the singular flag may also be combined with that list. Only explicitly selected
roots and their canonical descendants are eligible. Symlink escapes, sibling-prefix paths, vault
subdirectories and other installed vaults are rejected by the existing bridge.
The same bridge controls are exposed as Pi flags: `--beyin-bridge-context-chars N`
sets the startup budget (0–4000, default 1500; 0 suppresses injection), and
`--beyin-bridge-events SessionStart,SessionEnd` narrows the allowed events
(default SessionStart,Stop,PreCompact,SessionEnd). Invalid roots, budgets or event
names make the external adapter inert rather than broadening its scope.
No global Pi configuration is changed. You may explicitly add the extension path
to your personal Pi settings, but still supply a scoped root; the installer will
not maintain a copied global extension. Pi refuses to start when two extension
files register the same flag, so when several Beyin extensions load in one Pi
process (that personal path plus another trusted vault in cwd), the first one owns
the flags and lends them to the others over `pi.events`. Each vault still serves
only its own exact cwd, only the flag owner runs the external bridge, and a second
copy of an already loaded vault stays inert.

This mode uses `beyin_v3_bridge.py --harness pi`. Like the other global bridges it
records SessionStart/Stop/PreCompact/SessionEnd metadata and delivers only the small
startup bootstrap with the central CLI path and project-namespaced receipt session.
It does not automatically inject the entire companion or per-turn vault retrieval,
and does not track external editor results or force receipt reminders. Explicit
`context --project PROJECT` and source-backed receipts remain available. Optional
`preferences --project-context on` adds the existing bounded, visibility-filtered
same-project block. This is intentionally not identical to vault-local injection.
Pi does not consume hook JSON: bridge `--print-config --harness pi` is unsupported.

## Validation

`tests/v3_pi_test.py` installs synthetic vaults and checks CLI/context/receipt/doctor,
shared reminder behavior, exclusions/custom edits, package update/rollback and
uninstall. With Bun installed it also imports the generated extension, drives real
Pi-shaped event payloads, verifies the once-only continuation, fail-open transport,
path aliases, opt-out and external project boundaries. Bun is a test runner, not a
runtime dependency (Pi loads the extension itself).

```sh
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s tests -p 'v3_pi_test.py'
```

An optional offline host check uses an already installed Pi package, without loading
account settings or making model calls:

```sh
PI_TEST_PACKAGE=/absolute/path/to/node_modules/@earendil-works/pi-coding-agent \
  PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s tests -p 'v3_pi_test.py'
```

On 2026-10-17 the expanded Pi suite passed 20/20 on Linux, including the actual
Pi 1.3.0 loader/`ExtensionRunner`, profile/bridge/no-memory comparisons, an unrelated
second-user installation, bounded reminder continuation, editor-notice delivery and
preserved structured output. The shared hygiene suite passed 35/35.

An earlier V3 run hit an environment error: missing `libtk8.6.so` in the
unrelated Yakala font test; the same error was reproduced from the unchanged
`5328094` tree. After the operator installed Tcl/Tk 8.6, the targeted test passed
and the complete unfiltered V3 run succeeded: 1645 tests, 1615 passed and 30
platform/optional skips, with no explicit exclusions. These are local offline
results, not a native Windows/macOS or live paid-model claim. The frozen retrieval
evaluator passed all 16 development/holdout cases. A candidate
ZIP built from this branch also passed the release verifier against a locally built
`5328094` baseline (clean install, upgrade, rollback, interrupted recovery and user
note preservation). Those ZIP version labels were test-only, not a published release.

### Live Linux acceptance, 2026-10-17

A fresh Pi 1.3.0 RPC process using `openai/gpt-6.1-sol` passed the complete
vault-local lifecycle in an independently installed synthetic vault:

- A random source-backed canary was answered without tool calls; a private sentinel
  was absent from injected context. Neither expected value was included in the prompt.
- Real `write` and `edit` calls changed only a synthetic note. The opt-in large-note
  warning reached the tool results without replacing the original editor output.
- Stop added exactly one persisted reminder and continued the model. The model's
  shell call submitted a receipt with `harness=pi`, the actual hashed session, and
  the edited source ref. It was not fabricated by the test controller.
- RPC `compact` generated a real model summary and persisted a compaction entry.
  A later prompt returned the canary/source without tools or a duplicate receipt.
- Normal stdin closure delivered SessionEnd. All six lifecycle event types were
  acknowledged: 12 events, no pending events, no hook error. A pre-existing
  synthetic note retained its SHA256.
- Separate live `--beyin-no-memory` and outside-scope/no-root runs injected no
  context and left the acknowledgement count unchanged. An explicitly scoped
  external project received only its startup CLI/project/session bootstrap and
  added three boundary acknowledgements, not companion or per-turn retrieval.
- A second independently installed synthetic vault exercised shell `note-create`
  without an editor event. The real Pi shell session opened the edit window;
  receipt and learning reminders each continued the model once. The model submitted
  exactly one Pi receipt, wrote a source-linked knowledge note, and settled. Seven
  events were acknowledged, with no pending events or hook error.

The first live edit run exposed a real bug: checking the pre-reminder
`context.canContinue` suppressed reminders after normal assistant replies. Two
regression checks failed before the fix and passed after it; the successful live
run used a fresh installation of the corrected planner.
[Sanitized evidence and tested source hashes](evidence/pi-live-linux.json).

To repeat, install into a disposable synthetic vault/state, index a random internal
canary plus a private sentinel, enable the optional word-cap warning, and lower
`compaction.keepRecentTokens` in that fixture's `.pi/settings.json` (512 was used).
Review and approve only the generated synthetic resources; no trust hashes or
personal settings are modified. Launch with `--mode rpc --no-extensions -e
/path/to/synthetic-vault/.pi/extensions/beyin-v3.ts --no-skills --no-context-files
--tools read,write,edit,bash --session-dir /private/test-sessions`. Send prompts and
wait for `agent_settled`, not merely `agent_end`. Use RPC `get_entries` to verify
the reminder, then `compact`, then a no-tools follow-up prompt. Close stdin for
shutdown and inspect `doctor` plus the actual receipt source. For positional
prompts after extension boolean flags, separate them with `--`.

This establishes local Linux CLI/RPC delivery with an explicitly loaded extension,
not interactive TUI auto-discovery/trust UI or native Windows/macOS behavior.
It does not redeploy the corrected adapter into existing operator installations.
Handler/runner tests remain the evidence for synthetic failures and the broader
profile/distribution matrix. No remote CI or published-release claim is made.
